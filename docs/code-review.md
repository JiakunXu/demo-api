# 代码审查指南

## 审查输入

读取需求、差异、调用方和测试；以用户期待的行为和实际源码为依据。明确改动范围及既有用户修改，避免把无关历史问题作为本次新增缺陷。

## 优先检查

| 风险 | 具体问题与验证方向 |
| --- | --- |
| 权限和数据范围 | 用户/企业条件是否遗漏，审计人是否可信，跨企业请求是否拒绝 |
| 持久化 | 软删除、生成 ID、默认值、批量失败和零影响行是否保持契约 |
| SQL | Mapper 是否绑定，动态参数是否安全，count/list 条件是否一致 |
| API | long 计数是否截断，分页是否变无界，日期/null/错误码是否改变 |
| 事务与外部状态 | MQ/Redis 是否早于提交，失败和重复是否造成不一致 |
| 支付与回调 | 原始体、验签、金额、身份、状态和重复通知是否覆盖 |
| 测试 | mock 是否隐藏新行为，目标是否执行，有无真实外部依赖 |
| 文档和交付 | 命令和现状是否准确，配置/迁移说明是否同步 |

先报告可证明的正确性、安全性和兼容性问题，风格偏好不作阻塞。无法确定的行为说明假设及需要的证据，不虚构统一规范。

## 发现的表述

每项包括严重程度、最小文件/行号范围、具体触发条件、实际后果和修复方向。例如：某接口允许客户端提供企业 ID 而未校验归属，另一个企业用户可触发越权更新；建议将可信企业条件加入更新 WHERE 并补充跨企业回归用例。

不要只写“存在风险”或“建议优化”。审查无发现时也说明覆盖范围及未运行的验证，不能把无发现等同于绝对正确。

## 交付证据

说明实际测试命令、执行数量和结果；编译、单元测试、数据库验证、应用启动分别报告。当前 CI 有 CodeQL 与 Dependency Review 配置，未配置专门单元测试门禁，不能宣称 CI 已保证测试通过。

Codex 的自动审查入口仍参考根 `AGENTS.md` 中的 Review guidelines；本页供专项阅读，不假定单独被自动加载。PR 使用 [模板](../.github/PULL_REQUEST_TEMPLATE/pull_request_template.md)。
